## Q0 — Vue d'ensemble : quels outils permettent de rigger et d'animer EN CONTINU des personnages peints dans un pipeline navigateur headless, et sous quelles licences (code, runtime, éditeur) ?

### Takeaway
Aucun outil ne réunit à la fois licence permissive (code + runtime + éditeur), runtime web déterministe, auto-rig depuis un dessin unique et bonne tenue sur de l'art peint. La voie la plus sûre juridiquement est un rig cut-out/maillage maison sur PixiJS ou three.js (MIT), nourri d'algorithmes libres (ARAP MIT d'Animated Drawings, triangulation ISC/BSD) ; l'écosystème Inochi2D/nijilive (BSD-2) et le convertisseur image2live2d (Apache-2.0) sont les briques ouvertes les plus prometteuses pour fabriquer automatiquement une marionnette à partir de calques ; Spine, Live2D, l'export Rive, GSAP et Remotion portent des contraintes de licence.

### Inferences
- Pour un pipeline « évaluer(t) pur » et des licences MIT/Apache/BSD, les seules piles complètes sans contrainte sont : rendu PixiJS ou three.js + rig maison (os 2D, LBS, ARAP) + éventuellement anime.js pour les courbes d'accélération ; tout outil à éditeur propriétaire (Spine, Live2D, Rive pour l'export, DragonBones Pro) crée une dépendance humaine (rigger à la main dans une interface) incompatible avec « un film en minutes, sans intervention ».
- Les formats ouverts de marionnette à maillages (INP Inochi2D / nijilive) sont la meilleure option d'échange si l'on veut un jour un éditeur visuel libre ; mais aucun runtime web mature n'existe en octobre 2026 (inox2d prototype, nicxlive en développement) : il faudrait écrire un lecteur INP minimal en three.js/Pixi.
- Rive est techniquement excellent (os + maillages pondérés sur images, runtime MIT déterministe), mais la production de chaque fichier .riv exige l'éditeur et, depuis octobre 2025, un abonnement payant pour exporter : contraire à la consigne « gratuit, sans abonnement ».

## Q1 — Inochi2D (Inochi Creator, inox2d) : licence, état en 2026, rendu headless/navigateur, construction programmatique depuis des PNG en calques, runtime web ?

### Takeaway
Tout l'écosystème est sous BSD-2-Clause (compatible). La bibliothèque de référence en D est vivante (refonte « node graph » en octobre 2026), mais l'éditeur officiel Inochi Creator stagne depuis 2025 et le runtime Rust inox2d reste un prototype (WebGL/WASM oui, animations non). Le fork nijilive/nijigenerate (BSD-2) est le plus actif, et image2live2d (Apache-2.0) construit déjà, sans interface, une marionnette .inp à partir de calques PNG nommés.

### Cited Findings
- Inochi2D = « bibliothèque d'animation de marionnettes 2D en temps réel et implémentation de référence du standard Inochi2D Puppet ; déforme des maillages 2D créés à partir d'art en calques, selon des paramètres » — [README inochi2d](https://raw.githubusercontent.com/Inochi2D/inochi2d/HEAD/README.md).
- Licence BSD 2-Clause, « Copyright (c) 2020-2026, Inochi2D Project » — [LICENSE inochi2d](https://raw.githubusercontent.com/Inochi2D/inochi2d/HEAD/LICENSE).
- Activité de la lib : commits du 03/10/2026 (« Add core macro node graph », « Add initial macro-based parameter type »), 15/09/2026 (« Refactor deformation »), juillet 2026 (« Make a very basic example renderer in C », « Update C FFI ») ; dernier tag v0.8.7 — [dépôt Inochi2D/inochi2d](https://github.com/Inochi2D/inochi2d).
- La lib s'utilise hors du langage D via une FFI C (`dub build --config=dynamic`, compilateur LDC2), avec des liaisons officielles Unity — [README inochi2d](https://raw.githubusercontent.com/Inochi2D/inochi2d/HEAD/README.md).
- Inochi Creator : BSD-2 ; branche par défaut `v0_8` (dernier commit 12/03/2025, tag v0.8.6), branche `retooling` (dernier commit 16/06/2025, « new pseudo widget system (WIP) »), branche `main` figée au 11/08/2023 — [dépôt Inochi2D/inochi-creator](https://github.com/Inochi2D/inochi-creator) ; Inochi Session BSD-2, v0.8.7, commit 08/11/2025 — [dépôt inochi-session](https://github.com/Inochi2D/inochi-session).
- inox2d : « portage Rust expérimental officiellement soutenu » ; « cette bibliothèque et la spécification sont à l'état de prototype, usage en production non recommandé » ; lit les formats INP et INX ; rendu OpenGL ✅ et WASM (WebGL) ✅ ; paramètres (déformations de sommets, valeurs de transformation) ✅ ; physique ✅ ; animations ❌ ; mesh groups ❌ ; exemple `examples/render-webgl` — [README inox2d](https://raw.githubusercontent.com/Inochi2D/inox2d/HEAD/README.md).
- inox2d : licence BSD à 2 conditions — [LICENSE inox2d](https://raw.githubusercontent.com/Inochi2D/inox2d/HEAD/LICENSE) ; derniers commits 23/09/2026 (correctif NaN d'interpolation), 14/03/2026, 23/02/2026 (index de sommets en 32 bits) ; seul tag v0.3.0 — [dépôt inox2d](https://github.com/Inochi2D/inox2d).
- nijilive = fork : « bibliothèque d'animation de marionnettes 2D… implémentation de référence du standard nijilive Puppet » ; l'éditeur nijigenerate est « dérivé de la technologie Inochi2D (v0.8) » ; une implémentation C++ « nicxlive » est en développement et « fonctionne avec OpenGL, Vulkan, DirectX, Unity et WebGL » — [README nijilive](https://raw.githubusercontent.com/nijigenerate/nijilive/HEAD/README.md) ; [README nijigenerate](https://raw.githubusercontent.com/nijigenerate/nijigenerate/HEAD/README.md).
- nijilive : BSD-2, tag v1.0.0-beta1, commit 10/10/2026 ; nijigenerate : BSD-2, tag v1.0.0-beta4, commit 13/10/2026, « pas de version stable officielle pour l'instant », builds nocturnes ; dépend d'un fork `psd-d` (lecture PSD) — [dépôt nijilive](https://github.com/nijigenerate/nijilive) ; [dépôt nijigenerate](https://github.com/nijigenerate/nijigenerate).
- image2live2d (Apache-2.0, commit 07/09/2026) : « transforme une illustration en marionnette 2D riggable » ; entrée = calques déjà séparés (PSD, ou dossier/zip de fichiers `{ordre}_{rôle}.png` comme `00_hair_back.png`, `13_face_base.png`) ; les noms de calques pilotent la détection des rôles, le maillage et l'écriture du rig ; sorties : `.inp` nijilive (« Mature »), bundle Live2D `.moc3` (« validé octet par octet contre 5 modèles officiels »), projet Cubism `.cmo3` (expérimental) ; CLI `python -m image2live2d path/to/layers -o character.inp`, traitement par lot avec rapport de réussite ; pipeline `ingest → preprocess → decompose → mesh → rig authoring → physics → motion → IRR` — [README image2live2d](https://raw.githubusercontent.com/Wzhang3912/image2live2d/HEAD/README.md) ; [dépôt](https://github.com/Wzhang3912/image2live2d).
- Ce que fait la marionnette générée par image2live2d : clignement par œil (échange vers l'art « œil fermé »), bouche a-i-u-e-o, rotation de tête sur un dôme de profondeur, balancement et respiration du corps, « articulation des bras et des jambes autour des articulations de la silhouette », physique cheveux/jupe ; boucle d'attente ; rapport de capacités par personnage ; « généralise au-delà de l'anime » (mascottes non humaines) et « se dégrade proprement » — [README image2live2d](https://raw.githubusercontent.com/Wzhang3912/image2live2d/HEAD/README.md).
- Pour partir d'une image unique non découpée, image2live2d appelle un service See-through de décomposition (GPU) — [README image2live2d](https://raw.githubusercontent.com/Wzhang3912/image2live2d/HEAD/README.md).

### Inferences
- Construire une marionnette par programme à partir de PNG en calques est démontré (image2live2d → .inp). Pour la troupe MASSAMBA, le prérequis est d'avoir des calques par membre ; or les planches actuelles sont un dessin entier par pose (voir Q7 pour la décomposition).
- Rendu headless : l'exemple WebGL d'inox2d devrait tourner dans Chromium headless via SwiftShader (WebGL logiciel), mais il ne joue pas les animations ; il faudrait piloter les paramètres soi-même à chaque instant t — ce qui convient à un `evaluate(t)` maison. Non testé ici.
- Le modèle Inochi2D (déformations par paramètres + interpolation entre clés) est surtout pensé pour visage/buste (VTubing) ; pour un corps entier avec marche, il faut ajouter des os/rotations ; image2live2d annonce l'articulation bras/jambes, à vérifier sur un vrai personnage de la troupe.

### Gaps
- Spécification exacte du format INP (structure JSON + textures) non lue dans cette session ; la possibilité de générer un .inp sans image2live2d (écriture directe) reste à confirmer.
- Import PSD/KRA et maillage automatique dans Inochi Creator : aucune documentation officielle trouvée par la recherche (seules des pages Live2D sont remontées).
- Aucun test réel d'inox2d WASM ou de nicxlive WebGL dans Chromium headless.

## Q2 — Meta « Animated Drawings » : licences (code et modèles), segmentation, maillage, ARAP, reciblage BVH, vitesse CPU, tenue sur des personnages peints, maintenance

### Takeaway
Tout est sous MIT (code, poids des modèles, jeu de données Amateur Drawings). La chaîne est simple et réutilisable : détection + pose par modèles OpenMMLab servis par TorchServe, segmentation par traitement d'image classique, maillage par Delaunay, déformation ARAP (Igarashi 2009), reciblage BVH. Mais la pile est figée (Python 3.8, torch 2.0, mmcv 1.7), la maintenance est minimale (une seule release v0.0.1) et la vitesse CPU n'est pas documentée.

### Cited Findings
- Licence : « Animated Drawings code, model weights, and Amateur Drawings dataset is released under the MIT license » ; ChildlikeSHAPES sous CC-BY 4.0 ; les fichiers .mar ont été produits avec OpenMMLab (MMDetection et MMPose, Apache-2.0) — [README AnimatedDrawings](https://raw.githubusercontent.com/facebookresearch/AnimatedDrawings/HEAD/README.md) ; [LICENSE MIT](https://raw.githubusercontent.com/facebookresearch/AnimatedDrawings/HEAD/LICENSE).
- Article : « A Method for Animating Children's Drawings of the Human Figure », ACM TOG 42(3), 2023 ; jeu de données de plus de 178 000 dessins amateurs annotés (boîtes, masques, articulations) ; technique de reciblage « twisted perspective » — [README AnimatedDrawings](https://raw.githubusercontent.com/facebookresearch/AnimatedDrawings/HEAD/README.md).
- Modèles : `drawn_humanoid_detector.mar` et `drawn_humanoid_pose_estimator.mar` téléchargés depuis la release v0.0.1, servis par TorchServe dans Docker (image miniconda, Python 3.8.13, torch 2.0.0, mmcv-full 1.7.0, mmdet 2.27.0, mmpose 0.29.0) — [Dockerfile torchserve](https://raw.githubusercontent.com/facebookresearch/AnimatedDrawings/HEAD/torchserve/Dockerfile) ; le README conseille de monter la mémoire Docker à 16 Go si TorchServe échoue — [README](https://raw.githubusercontent.com/facebookresearch/AnimatedDrawings/HEAD/README.md).
- Segmentation : fonction `segment()` = seuillage, opérations morphologiques (fermeture, dilatation), remplissages par diffusion depuis les bords, puis conservation du plus grand contour (`skimage.measure.find_contours`) — [image_to_annotations.py](https://raw.githubusercontent.com/facebookresearch/AnimatedDrawings/HEAD/examples/image_to_annotations.py).
- Maillage : `scipy.spatial.Delaunay` + `shapely` dans `animated_drawing.py` ; un personnage = maillage 2D texturé par le dessin + squelette + module ARAP qui déforme le maillage d'après les positions des articulations — [animated_drawing.py](https://raw.githubusercontent.com/facebookresearch/AnimatedDrawings/HEAD/animated_drawings/model/animated_drawing.py).
- ARAP : implémentation Python (scipy.sparse) de Igarashi & Igarashi, « Implementing As-Rigid-As-Possible Shape Manipulation and Surface Flattening », JGT 14(1), 2009 ; deux résolutions successives (la 2ᵉ réutilise les rotations par arête de la 1ʳᵉ) pour rendre la rotation libre et pénaliser l'étirement — [arap.py](https://raw.githubusercontent.com/facebookresearch/AnimatedDrawings/HEAD/animated_drawings/model/arap.py).
- Mouvement : fichiers BVH d'acteurs humains rejoués et reciblés (`retargeter.py`, `bvh.py`) ; exemples quadrupède, six bras, plusieurs personnages, Rokoko — [arborescence du dépôt](https://github.com/facebookresearch/AnimatedDrawings) ; export MP4 ou GIF transparent ; rendu headless avec `USE_MESA: True` — [README](https://raw.githubusercontent.com/facebookresearch/AnimatedDrawings/HEAD/README.md).
- Dépendances figées : numpy 1.24.4, scipy 1.10.0, opencv-python 4.6.0.66, PyOpenGL 3.1.6, glfw 2.5.5, torchserve 0.12.0 — [setup.py](https://raw.githubusercontent.com/facebookresearch/AnimatedDrawings/HEAD/setup.py) ; testé seulement sur macOS Ventura 13.2.1 et Ubuntu 18.04 — [README](https://raw.githubusercontent.com/facebookresearch/AnimatedDrawings/HEAD/README.md).
- Maintenance : dernier commit 03/09/2025, unique tag v0.0.1 — [dépôt](https://github.com/facebookresearch/AnimatedDrawings).
- Les masques et articulations prédits peuvent être corrigés à la main (`fix_annotations.py`, interface web) avant `annotations_to_animation.py` — [README](https://raw.githubusercontent.com/facebookresearch/AnimatedDrawings/HEAD/README.md).

### Inferences
- Pour des PNG peints avec canal alpha, l'étape de segmentation par seuillage est inutile : le masque se lit directement dans l'alpha ; on peut ne garder que (a) l'estimation des articulations (ou une pose fixée à la main une fois par personnage), (b) Delaunay + ARAP, (c) le reciblage. Ces trois blocs sont MIT et portables en JavaScript.
- La pile Python d'origine (3.8, mmcv 1.7) n'est vraisemblablement pas installable telle quelle sur Python 3.12 ; mieux vaut porter l'algorithme qu'exécuter le dépôt.
- Limite de fond pour la troupe : ARAP déforme UNE silhouette ; quand un bras passe devant le torse, il n'y a pas de pixels cachés (occlusion) — il faut des calques séparés et un remplissage (inpainting), sinon le bras « tire » le torse avec lui. Animated Drawings contourne cela par le « twisted perspective » et des dessins d'enfants plutôt frontaux.

### Gaps
- Aucune mesure publiée de la vitesse CPU (détection, pose, ARAP par image) trouvée ; à mesurer.
- Aucun test public trouvé sur des personnages peints couleur style Pixar/Afrikatoon ; le détecteur a été entraîné sur des dessins amateurs — tenue inconnue sur nos planches.

## Q4 — PixiJS v8 (MIT) : Mesh/MeshPlane/MeshRope, plugins squelettiques, rendu Node/headless, vitesse face à three.js pour le compositing 2D en calques

### Takeaway
PixiJS v8 (MIT, 8.22.0 du 01/10/2026) offre exactement les primitives d'un rig cut-out à maillage (MeshSimple avec sommets modifiables à chaque image, MeshPlane, MeshRope, PerspectiveMesh, shaders personnalisés). Notre mesure dans le conteneur (SwiftShader, 4 cœurs) ne montre PAS d'écart net de vitesse avec three.js r186 : le coût est dominé par la rastérisation logicielle des calques et la relecture des pixels (≈ 80 à 270 ms par image 576×1024 avec 14 calques déformés, très bruité). Changer de moteur ne suffira pas à rendre le rendu « en minutes » ; il faut agir sur la charge de rastérisation et le parallélisme.

### Cited Findings
- Classes de maillage v8 : `Mesh` (géométrie + shader, état GPU), `MeshGeometry` (positions 2 flottants/sommet, uvs, indices), `MeshSimple` (tableaux directs, `autoUpdate = true` pour mise à jour à chaque image via `mesh.vertices`), `MeshRope` (texture le long d'une suite de points), `MeshPlane` (quad subdivisé `verticesX`/`verticesY` pour déformation en grille), `PerspectiveMesh` (`setCorners`) ; shaders via `Shader.from({ gl: { vertex, fragment }, resources })` — [PixiJS v8, Mesh](https://pixijs.com/8.x/guides/components/scene-objects/mesh).
- `pixi.js` 8.22.0 publié le 01/10/2026, MIT ; dépôt actif (commit 10/10/2026, branche dev) — [npm](https://registry.npmjs.org/pixi.js) ; [dépôt](https://github.com/pixijs/pixijs).
- `@pixi/node` 8.0.0 (19/04/2026, MIT) pour Node : repose sur les paquets natifs `gl` (headless-gl) et `canvas` (node-canvas), avec compilation depuis les sources si l'environnement n'a pas de binaire précompilé — [README @pixi/node](https://raw.githubusercontent.com/pixijs-userland/node/HEAD/README.md) ; [npm](https://registry.npmjs.org/@pixi%2Fnode).
- Plugins squelettiques Pixi v8 : `@esotericsoftware/spine-pixi-v8` 4.3.13 (licence Spine ⚠) — [npm](https://registry.npmjs.org/@esotericsoftware%2Fspine-pixi-v8) ; `dragonbones-pixijs` 1.0.5 (ISC) — [npm](https://registry.npmjs.org/dragonbones-pixijs) ; `untitled-pixi-live2d-engine` 1.4.0 (MIT, Core Live2D propriétaire requis) — [npm](https://registry.npmjs.org/untitled-pixi-live2d-engine).
- three.js 0.186.1 (r186), MIT, publié le 24/09/2026 — [npm](https://registry.npmjs.org/three).
- **Mesure maison (16/10/2026)** — Chromium Playwright `chromium-1194` headless, rendu WebGL confirmé « ANGLE (Google, Vulkan 1.3.0 (SwiftShader Device (Subzero)), SwiftShader driver) », 4 cœurs (`nproc`) ; scène identique dans les deux moteurs : 14 calques texturés (textures 512×512 peintes procéduralement), 561 sommets par calque (grille 16×32), déformation CPU de type LBS (rotation autour d'un pivot haut, fonction pure de t) à chaque image, toile 576×1024, 150 images, relecture `gl.readPixels` à chaque image. Temps moyen par image (rendu + relecture), quatre passes : **PixiJS 8.22.0 = 78,7 / 142,8 / 167,9 / 206,9 ms** ; **three.js r186 = 77,6 / 179,8 / 193,5 / 267,2 ms**. Relecture seule (clear + readPixels) = 5,0 ms. Toile Canvas 2D en cut-out rigide (drawImage + matrice affine, 14 calques) + `getImageData` = 104,0 ms. Sans relecture, `gl.finish()` ne bloque pas (0,3 à 1,7 ms mesurés, non significatifs) — [script de mesure : scratchpad de session `rig/benchsrc/www/bench.html` et `rig/benchsrc/run2.cjs`](file:///tmp/claude-0/-home-user-Add-a-README-file/b47568ca-f920-5025-9cd6-5f833e2dbfb0/scratchpad/rig/benchsrc/www/bench.html).
- Remotion signale le même goulot côté serveur : WebGL, Canvas 2D et certains effets CSS utilisent le GPU, et les instances cloud sans GPU en deviennent le goulot ; conseil : remplacer par des images précalculées — [Remotion, Performance](https://www.remotion.dev/docs/performance).

### Inferences
- À 80–270 ms par image, une minute à 30 i/s (1 800 images) coûte environ 2,4 à 8 minutes de rendu séquentiel dans ce conteneur : « en minutes » est atteignable, mais l'écart de moteur (Pixi vs three) est dans le bruit de mesure ; le gain viendra plutôt de : moins de surface rastérisée (rogner les textures aux pixels utiles, moins de recouvrements), précomposer les calques immobiles (décor, membres non animés) en une seule texture par plan, rendre plusieurs segments du film en parallèle (plusieurs pages/processus), et éviter une relecture synchrone à chaque image quand l'encodeur peut consommer directement la toile.
- Pour un projet déjà en three.js, rester sur three.js (MIT) est raisonnable : PixiJS n'apporte pas de vitesse mesurable ici ; son intérêt est l'API 2D (MeshSimple/MeshRope prêts, hiérarchie de conteneurs, masques) qui simplifie l'écriture d'un rig cut-out.
- `@pixi/node` dépend de modules natifs (`gl`, `canvas`) : le chemin « Chromium headless + SwiftShader » déjà en place est plus simple que Node pur.

### Gaps
- La mesure est très bruitée (facteur ×2,5 entre passes) : probablement la contention CPU du conteneur ; à refaire avec les vraies planches, plusieurs répétitions et la médiane.
- Le gain d'un rendu parallèle (plusieurs pages Chromium) sur 4 cœurs n'a pas été mesuré ; SwiftShader est déjà multi-fil, le gain peut être faible.
- Le moteur WebGPU de Pixi v8 (et de three.js) en headless sans GPU n'a pas été testé.

## Q6 — Algorithmes de déformation utilisables en JS (ARAP, poids biharmoniques bornés, LBS 2D), bibliothèques, poids automatiques depuis une silhouette, découpe automatique en membres (SAM/SAM2) et remplissage des zones cachées (inpainting)

### Takeaway
Il n'existe pas de bibliothèque JavaScript ARAP/« puppet warp » publiée sur npm (recherche du 16/10/2026) : il faut porter l'algorithme (la version Python MIT d'Animated Drawings est la meilleure base ; le portage Python « puppet-warp » est GPL-3.0, donc interdit ; libigl, qui contient les poids biharmoniques, est MPL-2.0, hors liste). Les briques de triangulation et de contour existent en ISC/BSD/MIT. Pour la découpe et le remplissage, SAM2 (code et poids Apache-2.0) et LaMa (Apache-2.0) passent la règle ; SAM 3 a une licence maison avec accès sur demande.

### Cited Findings
- ARAP (Igarashi, Moscovich, Hughes, SIGGRAPH 2005) : l'utilisateur déplace des poignées ; les autres sommets d'un maillage triangulaire sont calculés en minimisant la distorsion par triangle, en deux étapes à forme fermée (rotation puis échelle), assez rapide pour l'interactif — [SIGGRAPH History](https://history.siggraph.org/?p=113958).

### Inferences
- Pipeline libre plausible pour un rig « cut-out + peau souple » à partir d'un PNG peint détouré : contour par marching squares sur l'alpha (d3-contour, ISC) → simplification (simplify-js, BSD-2) → triangulation contrainte (poly2tri BSD-3 ou cdt2d MIT ; earcut/delaunator ISC) → poids de skinning automatiques maison (diffusion de chaleur / distance géodésique dans le maillage vers chaque os, faute de BBW sous licence permise) → LBS 2D sur GPU (three.js `SkinnedMesh` en caméra orthographique, ou MeshSimple Pixi mis à jour sur CPU) → ARAP porté depuis `arap.py` (MIT) pour les zones souples (ventre, joues, vêtements).
- ISC est fonctionnellement équivalente à MIT/BSD-2, mais ne figure pas littéralement dans la liste « MIT, Apache-2.0, BSD » du projet : à valider explicitement par l'utilisateur, sinon préférer poly2tri (BSD-3) et cdt2d (MIT).
- La découpe automatique d'une planche en membres demande (1) une segmentation par parties (SAM2 guidé par les articulations détectées) et (2) le remplissage des pixels cachés derrière les membres (LaMa) ; LaMa tourne raisonnablement sur CPU d'après l'usage courant, SAM2 aussi pour quelques images par personnage — à mesurer. Ce travail se fait UNE fois par personnage et par pose, pas à chaque image.

### Gaps
- Aucune mesure CPU (SAM2, LaMa, Qwen-Image-Layered) dans ce conteneur ; taille et faisabilité CPU de Qwen-Image-Layered non vérifiées (vraisemblablement GPU).
- Licence officielle des poids LaMa (dépôt d'origine) non vérifiée ; seul un miroir HF tiers a été lu.
- Pas d'implémentation libre (MIT/BSD/Apache) des poids biharmoniques bornés trouvée en JS ou WASM.

## Q7 — Projets 2025-2026 « image unique → marionnette 2D riggée » (et proches) : DrawingSpinUp, Make-It-Animatable, AniDoc, Sketch2Anim, CharacterGen, outils de découpe à base de SAM — licences et faisabilité

### Takeaway
Le front 2026 est la décomposition d'UNE illustration en calques complétés puis leur riggage automatique : See-through (SIGGRAPH 2026, code Apache-2.0, jusqu'à 23 calques inpaintés, poids partiellement OpenRAIL++), image2live2d (Apache-2.0, calques → marionnette .inp/.moc3 sans interface) et Bunraku (arXiv juillet 2026, calques + maillages + déplacements de sommets ; code non confirmé). Ces travaux visent l'anime et exigent un GPU pour la décomposition. Les autres projets cités (DrawingSpinUp, Make-It-Animatable, CharacterGen, UniRig) passent par la 3D ; AniDoc fait de la colorisation de lignes.

### Cited Findings
- **See-through** (Jian Lin et al., arXiv 2602.03749, février 2026, SIGGRAPH 2026) : décompose une image en calques sémantiques entièrement complétés (inpaintés) avec ordre de dessin inféré — jusqu'à 23 calques (cheveux, visage, yeux, vêtements, accessoires) ; supervision tirée de modèles Live2D commerciaux (ArtMesh) — [arXiv](https://arxiv.org/abs/2602.03749) ; [dépôt](https://github.com/shitagaki-lab/see-through).
- See-through : code Apache-2.0, commit 06/10/2026 ; pipeline principal `inference_psd.py` = modèle LayerDiff 3D (diffusion SDXL, calques transparents) + Marigold affiné (pseudo-profondeur) → PSD en couches ; dépendances optionnelles detectron2, SAM2, mmcv/mmdet ; démo Hugging Face ZeroGPU : « 1-2 extractions PSD par jour, environ 2-3 min chacune à 1280 px » — [README See-through](https://raw.githubusercontent.com/shitagaki-lab/see-through/HEAD/README.md) ; [LICENSE](https://raw.githubusercontent.com/shitagaki-lab/see-through/HEAD/LICENSE).
- Licences des poids See-through (API Hugging Face) : `layerdifforg/seethroughv0.0.2_layerdiff3d` = **openrail++** ⚠ ; `24yearsold/l2d_sam_iter2` (segmentation du corps) = apache-2.0 ; `24yearsold/seethroughv0.0.1_marigold` = non lisible par l'API ; base `prs-eth/marigold-depth-v1-0` = apache-2.0 — [layerdiff3d](https://huggingface.co/api/models/layerdifforg/seethroughv0.0.2_layerdiff3d) ; [l2d_sam_iter2](https://huggingface.co/api/models/24yearsold/l2d_sam_iter2) ; [marigold v1-0](https://huggingface.co/api/models/prs-eth/marigold-depth-v1-0).
- **image2live2d** (Apache-2.0) : calques séparés → rig complet (maillage, déformeurs clignement/bouche/rotation de tête, physique) → `.inp` nijilive, `.moc3`, `.cmo3`, « sans Cubism Editor, sans maillage manuel, sans rendu image par image » ; testé sur 16 styles, et sur des mascottes non humaines — [README image2live2d](https://raw.githubusercontent.com/Wzhang3912/image2live2d/HEAD/README.md).
- **Bunraku** (Junhao Chen et al., arXiv 2607.27348, 29/07/2026) : une illustration anime → calques RGBA ordonnés (parties cachées complétées), un maillage triangulaire par calque (depuis l'alpha), déplacements de sommets par pose-clé ; 2 étapes (diffusion en calques, puis prédiction conjointe des déplacements, chaque sommet = un jeton) ; nouveau benchmark Live2D-Bench et corpus de 8 884 modèles Live2D ; cosinus de direction moyen 0,768 sur 50 personnages ; publication de code/poids non confirmée, article sous CC BY-NC-SA 4.0 — [arXiv](https://arxiv.org/abs/2607.27348).
- **Textoon** (arXiv 2501.10020, janvier 2025) : génère des personnages Live2D depuis du texte « en moins d'une minute » — [arXiv](https://arxiv.org/html/2501.10020v2) ; dépôt (badge Apache-2.0, pas de fichier LICENSE détecté à la racine, dernier commit 02/07/2025) dépendant de ComfyUI, de checkpoints SDXL tiers (Civitai, Liblib) et d'un Qwen2.5-1.5B affiné ; sortie Live2D — [README Textoon](https://raw.githubusercontent.com/human3daigc/Textoon/HEAD/README.md).
- **DrawingSpinUp** (SIGGRAPH Asia 2024, arXiv 2409.08615) : animation 3D depuis un dessin unique ; aucun fichier LICENSE trouvé à la racine ; expériences sur RTX 4090 (2080 Ti possible), tiny-cuda-nn, Blender 3.6 pour le rendu ; commit 25/09/2026 — [arXiv](https://arxiv.org/pdf/2409.08615) ; [README](https://raw.githubusercontent.com/LordLiang/DrawingSpinUp/HEAD/README.md).
- **Make-It-Animatable** : MIT (2025), commit 08/09/2026 — [LICENSE](https://raw.githubusercontent.com/jasongzy/Make-It-Animatable/HEAD/LICENSE) ; **UniRig** : MIT, commit 04/06/2026 — [LICENSE](https://raw.githubusercontent.com/VAST-AI-Research/UniRig/HEAD/LICENSE) ; **CharacterGen** : Apache-2.0, commit 11/04/2025 — [LICENSE](https://raw.githubusercontent.com/zjp-shadow/CharacterGen/HEAD/LICENSE).
- **AniDoc** : badge Apache dans le README mais pas de fichier LICENSE à la racine ; entraînement 8×A100, inférence testée sur RTX 5000, ≈ 14 Go de VRAM ; dernier commit 15/04/2025 — [README AniDoc](https://raw.githubusercontent.com/yihao-meng/AniDoc/HEAD/README.md).
- **Qwen-Image-Layered** : décomposition d'image en calques, code et poids Apache-2.0 — [API HF](https://huggingface.co/api/models/Qwen/Qwen-Image-Layered) ; [LICENSE](https://raw.githubusercontent.com/QwenLM/Qwen-Image-Layered/HEAD/LICENSE).

### Inferences
- La chaîne la plus proche du besoin MASSAMBA est : planche peinte → décomposition en calques par membre avec zones cachées complétées (See-through ou Qwen-Image-Layered, GPU, une fois par personnage) → rig automatique (logique d'image2live2d, à adapter : os du corps entier plutôt que paramètres de visage) → rendu continu dans notre moteur web avec `evaluate(t)`.
- Risque de domaine : See-through et Bunraku sont entraînés sur des modèles Live2D d'anime ; un style peint africain type Pixar/Afrikatoon est probablement hors distribution — à tester sur 1-2 planches avant tout investissement.
- Confidentialité : envoyer des planches de l'utilisateur sur une démo publique Hugging Face/ModelScope est un transfert vers un tiers ; la règle du dépôt (images uniquement dans `workbench/.private/`) impose l'accord explicite de l'utilisateur, ou une exécution sur un GPU qu'il contrôle.
- Les poids LayerDiff 3D sous OpenRAIL++ (licence à restrictions d'usage) ne sont pas dans la liste MIT/Apache/BSD : à signaler ; Qwen-Image-Layered (Apache-2.0 code + poids) est l'alternative conforme pour la décomposition.
- Les approches 3D (Make-It-Animatable, UniRig, CharacterGen, DrawingSpinUp) servent plutôt la piste hybride « corps 3D, peau 2D » déjà explorée par le projet ; elles demandent un GPU.

### Gaps
- Sketch2Anim (SIGGRAPH 2025) et CartoonAlive (portrait → Live2D, 2025) n'ont pas été vérifiés (licences, code).
- Code et poids de Bunraku : publication non confirmée ; page projet non consultée.
- Aucun temps d'exécution CPU publié pour See-through ou Qwen-Image-Layered ; aucun test sur art peint non-anime.
- Licence du checkpoint Marigold affiné de See-through non lisible via l'API HF.
